App Ratings Analyzer

One private dashboard that turns scattered App Store signals into "what users hate vs. what they love."

The problem

Reviews, star ratings & downloads live in 3 disconnected Apple sources — and the per-star split has no API at all.

The solution

A self-hosted Node app that consolidates everything, stores it, and auto-generates a monthly insight report.

Business value

Product teams see pain points early — no SaaS fees, no private key in the browser, data stays yours.

Open with the one-liner: "Every product team drowns in App Store feedback but can't see the signal." This tool pulls an app's reviews, ratings and downloads into a single private dashboard and tells you, each month, the biggest pain points versus what users love. Motivation: I wanted Mixpanel-style insight for App Store feedback without paying a SaaS, and without ever exposing Apple's signing key to a browser. Business value in one breath: catch problems early, keep your data, zero recurring cost. (~55s)
What it does

Key features

Daily auto-sync

Incremental pull of new reviews (stops at a cutoff date), deduped by ID into the database.

AI insight report

Themed pain-points & praise with example quotes — LLM when configured, local heuristic otherwise.

Ratings over time

All-time total & average across storefronts, incl. star-only ratings the reviews API omits.

Downloads & adoption

Install totals + per-country breakdown + latest-version adoption from Sales Reports.

Screenshot OCR

Reads the per-star breakdown off an ASC screenshot locally (Tesseract) — the only way to get that data.

Alerts & export

Email on new reviews (Resend/SMTP), EN/DE UI, password login, one-click PDF export.

Don't read every card — group them. "Three pillars: it collects, it analyzes, it alerts." Collect: daily incremental sync, plus ratings and downloads from two more Apple sources. Analyze: the headline feature — a monthly themed report of pain points vs. praise with real quotes. The clever bit: Apple gives no per-star API, so we OCR the App Store Connect screenshot locally. Alert: email notifications, PDF export, bilingual UI. The point: it's not a dump of numbers, it's an opinion about what to fix next. (~60s)

Walk it left to right. Three Apple sources feed the Express backend. The backend signs every Apple request with an ES256 JWT server-side — the private key never reaches the browser, which was a hard requirement. The data layer is a facade: one async API, and a lazy driver picks SQLite locally or Postgres/Supabase in production, so the unused database dependency never even loads. The AI layer is pluggable — any OpenAI-compatible provider or a fully local heuristic. Frontend is deliberately build-free: plain HTML/CSS/JS. The scheduler runs either in-process or on GitHub Actions so the free host doesn't need to stay awake. (~60s)
Hard parts

Challenges & how they were solved

No per-star ratings API

Apple exposes the average, never the 5★…1★ split. Local Tesseract OCR of the ASC screenshot + a validated manual-snapshot endpoint.

Keep the signing key off the client

A leaked .p8 key is account-wide. All JWT signing is server-side; a boot guard refuses to start if key files are world-readable.

Free hosting sleeps

Render free tier cold-starts and can't run a reliable cron. Moved the daily job to GitHub Actions writing to Supabase; DISABLE_CRON=1 avoids double runs.

Flaky & varied data sources

Sales data lags 1–2 days; the reviews key may be missing; LLMs differ per provider. Graceful degradation everywhere + 6h caching; one code path for all OpenAI-compatible providers.

Four genuinely non-trivial problems. One: Apple simply has no per-star API, so I read it off a screenshot with local OCR — never uploaded — and let the user confirm before saving. Two: security — the signing key is account-wide, so signing is 100% server-side and the app won't even boot if the key file has loose permissions. Three: the free host falls asleep and can't cron reliably, so the daily job runs on GitHub Actions into Supabase, with a flag to prevent the in-process cron double-running. Four: every data source can fail differently, so the whole app degrades gracefully — a missing review key still lets you analyze stored data; no LLM key falls back to a local heuristic. (~60s)
What I'd keep doing

Lessons learned

  • Abstractions earn their keep. The DB facade made SQLite→Postgres a config flag, not a rewrite.
  • Design for absent config. Every optional feature (LLM, Sales, email, auth) degrades instead of crashing.
  • Validate at the edge. Bounded, sanitized payloads on write endpoints — defense-in-depth beyond parameterized queries.
  • Pluggable AI > one vendor. A single OpenAI-compatible path made swapping providers (incl. free Groq) trivial.
  • Push scheduling to the platform. CI cron + managed DB beat fighting a free host's lifecycle.
  • Boring frontend scales. No build step kept iteration fast and the deploy surface tiny.
The biggest lesson: a small, well-placed abstraction pays for itself. The database facade turned a scary "migrate to Postgres" into changing one environment variable. Second: treat missing configuration as a first-class state — optional features should disappear quietly, not throw. Third on the AI side: commit to an interface, not a vendor; the OpenAI-compatible shape let me use a free model in CI and a paid one elsewhere with zero code change. And on operations — don't fight your host; let GitHub Actions and Supabase own scheduling and state. Finally, a build-free frontend kept the whole thing fast to ship. (~55s)
